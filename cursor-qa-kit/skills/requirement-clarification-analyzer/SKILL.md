# 需求澄清分析

## 角色定位

以**测试工程师**视角工作：挖掘需求文档中的模糊地带、跨文档冲突、缺失规则；**对照产品 PRD 中的测试用例与验收标准**，判断期望是否已明确、是否与其他文档矛盾，整理成产品可直接澄清的问题清单。

## 分析步骤

### Step 1：读取所有相关文档

**读取顺序**（PRD 测试用例优先于功能描述）：

1. **产品 PRD（子 PRD + 父 PRD）** — 先定位测试章节，再读功能规则  
2. **已整理的测试需求** — `test/requirements/test_*-requirements.md`（若有）  
3. **后端接口文档**、**前端开发规范**

#### Step 1.0：检索 PRD 内嵌测试用例（强制执行，先于字段比对）

在 PRD 全文中检索以下关键词，**不得遗漏**任一测试/验收章节：

`验收标准`、`验收`、`测试用例`、`测试场景`、`Test Case`、`Acceptance`、`步骤`、`预期结果`、`期望结果`、`Given`、`When`、`Then`

重点阅读常见章节：`§7 验收标准`、`§7.x 测试用例 — …`、父 PRD `§5.4 逆向流程总表`（含操作与提示的条目纳入对照）。

### Step 1.5：建立 PRD 测试场景清单（强制执行，澄清前置门禁）

将 PRD 中**每一行**测试用例（表格的步骤/操作 + 预期结果，或列表的场景描述）登记为清单：

| PRD场景ID | 来源文档+章节+步骤号 | 操作/输入 | 预期结果（原文摘录） | 涉及功能点 |

- 为每条分配 ID，如 `TC-FORM-01`（功能缩写-序号）  
- **预期结果**尽量保留 PRD 原文，不 paraphrase  
- 统计 **N 条**，写入澄清文档文首 `PRD 测试场景数：N`

**原则**：
- PRD 测试用例中**已写明的期望** = 产品已定稿，**禁止**作为「待澄清」重复提问  
- 仅当 PRD **未写**且多文档冲突时，才列为待澄清  
- PRD 测试期望 vs 接口/前端/实现不一致 → **🔴**，必须并列引用 **PRD 步骤+预期原文** 与对方文档原文  
- **未完成本清单，不得进入 Step 2 写澄清问题**

### Step 1.6：输出「PRD 测试场景对照摘要」（强制执行）

澄清文档中**必须**包含该表（PRD 存在≥1 条测试用例时不可省略）：

| PRD场景ID | 来源 | 期望摘要 | 需求清单是否覆盖 | 结论（一致/遗漏/冲突/本期不测） |

### Step 2：逐字段交叉比对

对每个表单字段 / 功能点，横向比对所有文档，重点检查：

| 检查维度 | 说明 |
|---|---|
| **必填性冲突** | PRD / PRD测试用例 / API / 前端规范 是否一致 |
| **字符类型冲突** | |
| **长度限制冲突** | |
| **超出处理冲突** | |
| **流程冲突** | PRD 测试步骤描述的流程 vs 前端规范 |
| **期望冲突** | **PRD 测试用例「预期结果」** vs 接口文档或前端规范 |
| **字段缺失** | |
| **规则空白** | PRD 功能有描述但无测试期望、其他文档也无 |
| **范围未定义** | |
| **本期是否实现** | PRD 测试用例覆盖隐藏/未实现功能 → 🟢 确认项 |

### Step 2.5：PRD 测试场景覆盖度检查（强制执行）

将 PRD 测试场景清单与 `test_*-requirements.md`（或当前理解的需求范围）对照：

| 检查项 | 处理方式 |
|--------|----------|
| PRD 有场景、需求清单**未收录** | 澄清文档 **🟡** 增加「需求清单遗漏」：建议补入 requirements §9 或对应章节；**不是**向产品重复问期望 |
| PRD 期望与需求清单**不一致** | **🔴** 冲突项，引用双方原文 |
| PRD **无**测试用例但功能复杂 | **🟡** 建议产品补验收场景 |
| PRD 测试用例引用**已下线能力**（如本期隐藏的知识库上传） | **🟢** 确认项：测试用例是否需更新 |

### Step 2.6：输入框校验维度专项检查（强制执行）

> 对每个输入框检查校验时机、必填、格式、长度、多规则优先级；**若 PRD 测试用例已指定行为（如 disabled、截断、Toast），以 PRD 测试期望为对照基准**，仅当 PRD 未写且其他文档冲突时才列为待澄清。

（校验时机 / 必填 / 格式 / 长度 / 优先级 — 同原 2.5.1～2.5.5，略）

### Step 3：冲突分级

| 级别 | 标记 | 判断标准 |
|---|---|---|
| 高优先级 | 🔴 | 直接影响开发/测试；**含 PRD 测试期望与其他文档矛盾** |
| 中优先级 | 🟡 | 边界场景、**PRD 场景未纳入需求清单**、规则空白 |
| 低优先级 / 确认项 | 🟢 | PRD 测试用例过期、本期隐藏功能仍被验收等 |

### Step 4：生成澄清文档

输出路径（默认）：`{工作区根}/test/requirements/test_[功能名]-clarification.md`。若 `test/requirements/` 不存在则先创建。用户明确指定其他路径时从其指定。

## 注意事项

- **澄清需求 = 功能规则 + PRD 测试用例 双线分析**；只看 §3 业务规则、不看 §7 测试用例 = 不合格交付  
- 冲突描述须引用**原文**，**🔴 项必须含 PRD 测试表格中的步骤号与预期结果**  
- **禁止**把 PRD 测试用例已明确的期望再列为「待澄清」  
- 遵守 Rule：`~/.cursor/rules/requirement-clarification-standard.mdc`（`alwaysApply: true`）
- 每个问题必须说明**影响范围**
- 不替产品做决定，只提问题和影响
- 文件名必须以 `test_` 开头
- 若用户同时提供 `test_*-requirements.md`，澄清分析应**显式对照**该文件与 PRD 测试场景
